# Архитектура

## Основной принцип

Каналы, диалоговая логика, данные и доставка разделены. Особенности мессенджера заканчиваются в Channel Adapter, а остальные компоненты работают с общей моделью события.

~~~text
платформа
  → Channel Adapter
  → Privacy Gateway
  → Inbox
  → Dialogflow ES
  → Action Dispatcher
  → обычный сценарий / AI Module / состояние Manual Support
  → Outbox
  → Outbox Worker
  → Channel Router
  → Channel Adapter
  → платформа
~~~

## Компоненты

| Компонент | Ответственность |
| --- | --- |
| Channel Adapters | проверка события, нормализация, кнопки, вложения и отправка |
| Privacy Gateway | подготовка очищенного текста для внешних NLU/LLM |
| Inbox/Outbox | надёжный приём и доставка вне webhook-запроса |
| Dialogflow ES | определение intent и возврат action, fulfillment и parameters |
| Action Dispatcher | выполнение action: обычный сценарий, AI Module или смена режима |
| AI Modules | свободный fallback, база знаний и поиск мероприятий |
| Manual Support | состояние диалога, в котором автоматический ответ подавлен и работает сотрудник |
| Channel Router | выбор Channel Adapter только на этапе доставки |
| Admin UI / Admin API | поддержка, пользователи, настройки, события и аудит |
| PostgreSQL | долговечное бизнес-состояние |
| Redis | sessions, quotas, locks, rate limits и короткий AI-контекст |

## Почему архитектура гибридная

Обычное текстовое сообщение в автоматическом режиме сначала проходит через Dialogflow ES. NLU определяет intent и action, но не выполняет бизнес-сценарий. Этим занимается Action Dispatcher: он использует fulfillment Dialogflow, запускает настроенное действие или вызывает AI Module.

Manual Support не является альтернативным NLU-провайдером — это состояние диалога. В нём автоматический ответ подавляется, сообщения продолжают сохраняться для сотрудника, а специальный action может вернуть пользователя в режим ассистента. Ответ сотрудника проходит через тот же Outbox, что и автоматический ответ.

Channel Router не участвует в выборе intent или action. Он получает готовое исходящее сообщение после Outbox и выбирает sender зарегистрированного Channel Adapter по платформе назначения.

### Управляемые AI-модули

Общий профиль ассистента и база знаний настраиваются отдельно от правил конкретных AI Modules.

![Общие настройки профиля и стиля AI-модулей](<../images/Настройка общей информации для AI моудлей.png>)

_Профиль задаёт идентичность и общий стиль ответов, не смешивая их с задачами отдельных модулей._

![Управляемая база знаний для AI-модулей](<../images/База знаний для AI модулей.png>)

_База знаний редактируется из Admin UI и передаётся только в контролируемый контекст Assistant AI._

## Поиск мероприятий

Публичные источники обрабатываются отдельным extraction-pipeline. События сохраняются в PostgreSQL, фильтруются по времени и ранжируются текстовым и векторным поиском. Модель получает только небольшой набор кандидатов, а не всю базу.

![Список извлечённых мероприятий в панели управления](<../images/Панель управления мероприятия.png>)

_Сотрудник видит результат extraction-pipeline и может проверить данные, доступные ассистенту._

![Удаление неактуального мероприятия](<../images/Панель управления_Удаление мероприятия.png>)

_Отменённое или ошибочно извлечённое событие исключается из базы с явным указанием причины._

## Административный интерфейс

Desktop и VK Mini App используют общую логику чатов, но отдельные UI-компоненты. Realtime-обновления передают только тип изменения, после чего нужный экран выполняет целевой refetch.

![Закрытие обращения и возврат диалога в автоматический режим](<../images/Панель управления_Закрыти е обращения.png>)

_Закрытие обращения завершает Manual Support и возвращает диалог в автоматический режим._
