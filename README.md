# «Волга» — омниканальный ИИ-ассистент

> Ассистент и единый интерфейс поддержки для Центра развития креативных индустрий «Волга».

«Волга» — production-система, которая принимает обращения из официальных каналов организации, мгновенно отвечает на типовые вопросы и переводит диалог сотруднику, когда автоматического ответа недостаточно. Сотрудники работают с обращениями из разных мессенджеров в едином интерфейсе, не переключаясь между кабинетами платформ.

В основе продукта — последовательный гибридный pipeline: Dialogflow ES определяет intent и action, после чего Action Dispatcher запускает обычный сценарий, нужный AI Module или перевод в Manual Support. Inbox/Outbox, локальный Privacy Gateway и единая модель сообщений обеспечивают надёжность и безопасную работу с данными.

[Архитектура](docs/architecture.md) · [Надёжность и данные](docs/reliability-and-security.md) · [Эксплуатация](docs/production.md) · [Развитие продукта](docs/product-evolution.md)

> Важно: это публичный технический кейс без production-кода, реальных данных, внутренней инфраструктуры, endpoints и credentials.

## Задача и ценность

Значительная часть обращений повторяется: пользователи задают вопросы, ответы на которые уже опубликованы в сообществе или официальных источниках. Сотрудники тратят время на одинаковые ответы, хотя участие человека требуется только в отдельных случаях. Одновременно сообщение в официальном сообществе могло остаться незамеченным, и пользователь ждал ответа час или два.

Продукт решает обе проблемы:

1. **Снижает рутинную нагрузку.** NLU мгновенно отвечает на частые вопросы, а сотрудник подключается только к обращениям, где действительно нужен человек.
2. **Повышает качество сервиса.** Admin UI ускоряет реакцию поддержки, а AI Modules позволяют работать со свободными запросами и формировать персональные рекомендации.

## Что входит в продукт

Текущая версия объединяет:

- рабочие каналы VK и MAX и сохранённую интеграцию Telegram;
- Dialogflow ES для управляемых intent-сценариев;
- AI-fallback, базу знаний и персональный поиск мероприятий;
- единый интерфейс ручной поддержки;
- рассылки, согласия пользователей и audit trail;
- локальную защиту персональных данных;
- фоновые очереди, мониторинг, backup и автоматизированное развёртывание.

## Роль в проекте

Проект от идеи до работающей production-системы спроектирован и реализован мной самостоятельно: продуктовые сценарии, архитектура, backend, frontend, интеграции, модель данных, безопасность, тестирование и эксплуатационный контур.

Кейс показывает полный цикл создания продукта: от выявления реальной проблемы и проектирования пользовательского сценария до надёжной обработки сообщений, административного интерфейса и сопровождения после развёртывания.

## Архитектура

~~~mermaid
flowchart LR
    user[Пользователь] <--> platforms[VK / MAX / Telegram]
    platforms <--> adapters[Channel Adapters]
    adapters --> privacy[Privacy Gateway]
    privacy --> inbox[(Inbox / PostgreSQL)]
    inbox --> dialogflow[Dialogflow ES]
    dialogflow -->|intent + action + fulfillment| dispatcher[Action Dispatcher]

    dispatcher --> standard[Обычный сценарий]
    dispatcher --> ai[AI Modules]
    dispatcher --> manual[(Manual Support<br/>состояние диалога)]

    standard --> reply[Ответ]
    ai --> reply
    manual --> admin[Admin UI]
    admin --> reply

    reply --> outbox[(Outbox / PostgreSQL)]
    outbox --> router[Channel Router]
    router --> adapters
    redis[(Redis)] --- ai
~~~

### Путь сообщения

1. Channel Adapter проверяет событие и приводит его к общей модели.
2. Privacy Gateway создаёт очищенный текст для внешних NLU/LLM.
3. Исходный и очищенный текст вместе с Inbox job сохраняются одной транзакцией; только после этого webhook получает подтверждение.
4. Inbox Worker передаёт очищенный текст в Dialogflow ES.
5. Dialogflow ES возвращает intent, action, fulfillment и параметры.
6. Action Dispatcher готовит обычный ответ, вызывает соответствующий AI Module либо переводит диалог в состояние Manual Support.
7. Ответ и Outbox job атомарно сохраняются в PostgreSQL.
8. Outbox Worker передаёт сообщение в Channel Router, который выбирает Channel Adapter для нужной платформы.
9. В состоянии Manual Support сотрудник работает с диалогом через Admin UI, а его ответ проходит через тот же Outbox.

Подробнее: [архитектура системы](docs/architecture.md) и [жизненный цикл сообщения](diagrams/message-lifecycle.md).

## Техническая значимость

| Решение | Практический результат |
| --- | --- |
| Единая модель сообщений и Channel Adapters | продуктовая логика не дублируется между мессенджерами |
| PostgreSQL Inbox/Outbox | webhook не зависит от медленных API, принятые сообщения переживают сбои |
| Dialogflow ES → Action Dispatcher | intent/action отделены от выполнения бизнес-сценария |
| LLM только в отдельных AI Modules | интеллектуальные ответы не превращают весь продукт в недетерминированного агента |
| Manual Support как состояние диалога | автоматический и операторский режимы используют одну историю и доставку |
| Channel Router только в delivery flow | выбор платформы не смешан с маршрутизацией intent/action |
| Fail-closed Privacy Gateway | исходный текст не становится fallback для внешнего AI |
| PostgreSQL для истины, Redis для временного состояния | история не зависит от кэша, а quotas и locks остаются быстрыми |

Архитектура построена как модульный монолит: домены разделены внутри одного backend, а отдельно вынесены только компоненты с самостоятельными эксплуатационными требованиями. Это сохраняет управляемость системы без преждевременной сложности микросервисов.

### Интеллектуальный поиск мероприятий

Публичные источники обрабатываются отдельным extraction-pipeline. События сохраняются в PostgreSQL, фильтруются по времени и ранжируются полнотекстовым и векторным поиском. Модель получает только ограниченный набор кандидатов и отвечает на основе актуальных фактов.

### Единая операторская поверхность

Desktop-интерфейс и VK Mini App используют общую логику чатов, pagination, unread-состояний и realtime-обновлений, но разные UI-слои. Сотрудник работает с обращениями из нескольких каналов без перехода между кабинетами мессенджеров.

## Как развивался продукт

- **2025:** отдельный Telegram-бот с NLU отвечал на часто задаваемые вопросы.
- **Февраль–июнь 2026:** была спроектирована новая архитектура для официальных каналов, режимов диалога и собственного интерфейса поддержки.
- **Июль 2026:** новая омниканальная версия вошла в эксплуатацию.
- **Август 2026:** после внедрения AI Modules продукт был расширен базой знаний, интеллектуальным поиском мероприятий и единым privacy-контуром.

По мере развития собственный Rasa-контур был заменён Dialogflow ES, handoff tickets — режимом диалога, а прямые вызовы внешних API — Inbox/Outbox. Подробнее: [развитие продукта и принятых решений](docs/product-evolution.md).
